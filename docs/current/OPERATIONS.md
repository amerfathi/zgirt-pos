# التطوير والاختبار والنشر والتراجع

مرجع الإصدار 2.6.14 بتاريخ 2026-10-04. [الفهرس](../../README.md).

## تهيئة التطوير

استنسخ المستودع، وافحص الفرع و HEAD و`git status` قبل أي تعديل. استخدم Node.js24 و`npm ci` لاستعادة lockfile ، لا تحديث الاعتماديات تلقائيًا. `npm run dev` يشغّل الواجهة؛ لا يهيئ مصادقة أو D1 إنتاج. لا تضمّن اعتمادًا حقيقيًا في `.env` منشور أو fixture.

```sh
npm ci
npm run dev
npm run lint
npm run typecheck:core
npm run typecheck
npm test
npm run build
```

اختبارات API تستخدم workerd/Miniflare و D1/DO معزولين. `npm test` يشغّل security ثم integration ثم conflict-review ثم accounting. اقرأ اسم الملف والـ assertions قبل اعتبار الرقم تغطية لسيناريو مالي. فحوصات accounting الموروثة ليست رحلات واجهة كاملة حتى لو احتوى اسمها E2E.

## مصفوفة التحقق

لفحص التوثيق نفسه: `node scripts/verify-docs.cjs`. يتحقق من الروابط المحلية وتغطية الفهرس والتنبيهات التاريخية وأنماط الأسرار والإصدار وتنسيق النسخ؛ لا يشغّل العمليات المالية ولا يعد شهادة جديدة للتطبيق.

| الفحص | الأمر/الأداة | حد النتيجة |
|---|---|---|
| الجودة | lint/typecheck/build | لا يثبت صحة الأرقام وحده |
| المنطق والواجهات الداخلية | npm test | 259 حالة آلية و 17 فحص صيغة مستقل في لقطة الإصدار |
| تخزين المتصفح | test:browser-atomic ، test:browser-crash ، test:browser-idb-engine | أعطال/استرداد محددة، لا شهادة power-loss شاملة |
| التطبيق الدائم | test:browser-app-durable ، test:browser-cache-recovery | سيناريوهات التخزين/الترقية في الاختبار |
| تعدد الشركات والأجهزة | tests/platform-multi-company.mjs | واجهة فعلية؛ config خاصة بحسابات QA ، لا كلمات مرور في الأمر/التقرير |
| قرار المالك | tests/live-review-smoke.mjs | fixture QA ومصدران محفوظان واختيار صريح وإعادة سعر الاختبار |
| Android | ADB ومحاكي مخصص و WebView debug عند الاختبار | لا تفعّل remote debugging في APK الإنتاج |
| Windows | حزمة مستخرجة وملفات تعريف مؤقتة | لا يستبدل النسخة المثبتة للمستخدم |
| طباعة فعلية | طابعة وورقة وتدقيق النتيجة | لم تُعتمد في 2.6.14 |

لا تُنشئ QA داخل شركة المستخدم الحقيقي دون نطاق صريح. أسرار config ولقطات قاعدة البيانات تبقى في `scratch` ignored. مشاركة screenshot يجب أن تتجنب كلمات المرور والتوكنات وأي بيانات شخصية غير لازمة.

تحضير الحقول في اختبار نافذتي Windows يتم بالتتابع لأن التركيز على لوحة المفاتيح مشترك؛ حفظ الفواتير يبقى متزامنًا. سجّل المحاولة الفاشلة ثم سببها والتحقق اللاحق، لا تحذف دليل الفشل من التقرير.

## Android

يلزم Android SDK و JDK المناسب لإعداد Gradle. بيئة التحقق الحالية استعملت Android Studio JBR و Android36 ومحاكيات منفصلة. هذه مسارات جهاز المشغّل وليست شرطًا لكل مطوّر.

```sh
npm run build
npx cap sync android
cd android
```

ثم `gradlew.bat assembleDebug` على Windows أو `./gradlew assembleDebug` على بيئة مناسبة. للإنتاج، استخدم مسار GitHub المحمي وشهادة Android الأصلية؛ debug له شهادة مختلفة ولا يُركّب فوق release للتحديث. لا تمسح بيانات محاكي المستخدم للتغلب على اختلاف الشهادة؛ أنشئ محاكي QA مستقلًا.

مصدر Android: applicationId `com.khodar.pos`، versionName `2.6.14`، versionCode `26140`. يجب زيادة versionCode للإصدار التالي مع الحفاظ على التوقيع والهوية. فحص `apksigner verify --print-certs` وبيانات الحزمة مطلوب قبل النشر. شهادة 2.6.14 وبصمتها محفوظتان في تقرير الإصدار العام، لا keystore.

## Windows

`npm run electron:build` يتحقق من مفتاح التحديث العام ثم يبني Vite و NSIS. الأصول المتوقعة: `KhodarPOS-Setup.exe` و`windows-manifest.json`. توقيع البيان يتطلب مفتاحًا خاصًا مشفرًا محفوظًا في أسرار CI ، لا مفتاحًا جديدًا لتجاوز فشل التحقق.

اختبر version/url/size/SHA256 وتوقيع Ed25519 مع `electron/update-security.cjs`. بعد الرفع، قارِن digest وحجم كل أصل على GitHub بالأصل الذي اجتاز الاختبارات. لا تخلط صحة البيان مع توقيع Authenticode للمثبّت؛ الأخير غير متوفر. لا تثبّت فوق برنامج المستخدم أو تتجاوز تحذير النظام دون إذن مناسب.

مسار تشغيل التحديث والإغلاق والمثبّت في `electron/main.cjs` و`electron/installer.nsh`، واختبارات `update-installer.test.cjs` و`desktop-update-ui.test.mjs`. إصلاح الإغلاق سابقًا لا يثبت كل تثبيت مستقبلي أو كل مضاد فيروسات؛ اختبر الترقية الفعلية في بيئة مخصصة قبل اعتمادها.

## GitHub ونسخ الإصدارات

1. افحص الحالة وحدد ملفات المهمة فقط؛ لا تستخدم `git add -A` لالتقاط diagnostics قديمة.
2. حدّث الإصدار في package/package-lock و appVersion و Gradle بصورة متسقة، ثم نفّذ بوابات الجودة والاختبارات.
3. ارفع commit المصدر وفق حماية المستودع؛ لا تتجاوز رفض فرع محمي.
4. شغّل `production-release.yml` أولًا بـ publish=false و publish_metadata=false ، ونسختي staging بقيمة 0 لبناء الإصدار الحقيقي.
5. تحقّق من run الناجح و commit المصدر وشهادة APK و manifest و hash. اختبر الحزمة نفسها، لا debug بديلًا عنها.
6. انشر tag جديدًا وحزمًا immutable ؛ لا تستبدل أصول 2.6.13 أو 2.6.14 بتعديل لاحق.
7. إذا تأخر رفع Windows المحلي، يمكن `upload-verified-release.yml` استهلاك run ناجح من Production release/main. يتحقق من النسخة ومنشأ الحزمة والمفتاح/hash ، ويحتاج draft مربوطًا بالمصدر نفسه؛ لا يعيد بناء التطبيق ولا ينشر draft تلقائيًا. فشل validate يمنع upload.
8. قارِن digests العامة الثلاثة ثم انشر draft. بعدها فقط أعلن metadata في D1 باستخدام اعتماد محدود/مخوّل.

`scripts/publish-release-d1.cjs` ينشر metadata لـ Windows/Android بعد مطابقة بيان Windows بالحزمة. بيانات الويب تُنشر بمسار المشغّل المتحقق منه. السجلات لا تحتوي قيم الأسرار. بوابة`/api/releases/latest` يجب أن تعيد إصدارًا جديدًا للعميل الأقدم، و update=false للعميل الذي يملك الإصدار نفسه، وروابط تنزيل 200.

## Cloudflare والقاعدة الحية — تحذير حاسم

الإنتاج لا يستخدم جميع handlers الحالية في main. حزمة APIs المتوافقة موجودة في مساحة المشغّل `scratch/sync-hotfix-20261003`؛ baseline `c10f4e5` مع إصلاح المصادقة المجانية، مواءمة المبيعات المستقلة، proof العلاقات، والتسوية. ملفات UI الحالية نسخت إلى stage ، مع حفظ توافق push بلا متطلبات cash/timezone الجديدة.

هذا stage ignored ولا يستعاد كاملًا باستنساخ Git وحده؛ المستودع يوثّق المصدر والإصلاحات، لكنه **لا يملك بعد وصفة آلية عامة معتمدة تعيد تركيب APIstage**. على مشغّل جديد إعادة تركيبه ومقارنته مع handlers المراجعة واختباره أولًا، أو طلب نسخة تشغيل خاصة من المشغّل. لا تتجاوز هذه الفجوة بنشر main كاملًا؛ ضم stage كمسار reproducible يحتاج مهمة تقنية مستقلة.

قبل أي ترحيل: export إداري خاص، تحقق من حجمه/بصمته وصلاحية استرداده، ثم تمرين محلي للمخطط الفعلي. في 2.6.14 أضيفت فقط 0023–0026 وسُجلت بأسمائها؛ 0017–0022 لم تطبق. لا تشغّل `schema.sql` أو clean/resetscripts أو جميع migrations على قاعدة حيّة. وجود cashtables في المصدر لا يجيز تفعيل cash shifts.

Pages مشروع نشر مباشر؛ push إلى GitHub لا ينشر الويب تلقائيًا. بعد إعداد stage المتوافق و dist الفعلية والمصادقة لدى المشغّل، يكون أمر النشر من stage:

```sh
npx wrangler pages deploy dist --project-name khodar-pos --branch main --commit-dirty=true
```

يجب التحقق من deployment URL ومن موقع الإنتاج ومن APIs بعد النشر. لا ترسل OAuth/API token في الدردشة؛ إعداد الاعتماد يتم على جهاز المشغّل أو مخزن الأسرار. PASSWORD_CRYPTO binding يجب أن يشير إلى Worker الخاص المراجع؛ تغيير AUTH_SECRET يبطل الجلسات القائمة وليس خطوة توثيق عادية.

## التراجع والاستجابة للعطل

أبقِ tags والإصدارات السابقة و export قبل الترحيل وأرشيف الاسترداد. نقطة«restore point1»قرار تاريخي، وليست دليل وجود نسخة كاملة من D1 أو ملفات الجهاز؛ تحقق من refs والأصول الموجودة قبل الاعتماد عليها. Git يحفظ المصدر لا الاعتمادات ولا ملفات قاعدة المستخدم.

عند خلل: أوقف نشرًا جديدًا، سجّل نطاقه، واحتفظ بالعمليات المعلقة. التراجع عن frontend/API يجب أن يوافق مخطط قاعدة البيانات. لا تُسقط جداول جديدة أو receipts/financialsources لاستعادة كود قديم، ولا تحذف بيانات العميل. إن لزم إصدار native تراجع، يحتاج عادة إصدارًا أعلى يحمل إصلاحًا متوافقًا، لا downgrade يستبدل المراجع.

## المتابعة والتسليم

راقب 401/403/409/503 و Cloudflare1102 وحصص Free ، أحجام queue ، المصادر المحجوبة، أزمنة الإقرار وأخطاء quota. لا تُسجل payload مالي كاملًا أو token بلا حاجة. فحص الخمول النادر لا يعادل مراقبة تشغيل مركزية أو SLA. لا توجد شهادة حمل 1000 مستخدم.

حدّث دليل الإصدار وسجل الموانع و AI_HANDOFF مع HEAD/branch/status وأسماء الملفات غير المرفوعة وأول خطوة تالية؛ افحص الأسرار قبل commit. اختبارات مهمة التوثيق تتحقق من الروابط/تغطية الوثائق/الأسرار ولا تُعاد تسميتها اختبار تطبيق كامل.
