# المزامنة والحفظ والاسترداد

مرجع الإصدار 2.6.14 بتاريخ 2026-10-04. [الفهرس](../../README.md).

## قواعد لا تُكسر

1. العملية محفوظة فقط بعد إقرار الالتزام المحلي الدائم؛ لا تكفي رسالة الواجهة أو نجاح طلب الشبكة.
2. الحالة المالية والطابور والمؤشر ومعرفات المصادر المقبولة تُحفظ معًا في aggregate ، لا ككتابات منفصلة قد تنقطع بينها.
3. تكرار المصدر لا يُنتج أثرًا ماليًا ثانيًا. إقرار الخادم يزيل المصدر من الطابور بعد حفظ محلي ناجح فقط.
4. الشركة والفرع والمستخدم والصلاحيات تُراجع في الخادم والمحلي؛ تغيير واجهة الفرع لا يجيز مصدرًا أجنبيًا.
5. الفشل والتعارض والعلاقات المفقودة تحفظ الأدلة، ولا تستبدلها بسجل فارغ أو نتيجة نجاح زائفة.

## متى تعمل المزامنة؟

دفع العمليات الجديدة فوري عندما يتوفر الاتصال وتسمح حالة الخدمة، مع الاحتفاظ بالطابور وإعادة المحاولة عند الفشل. سحب التغييرات يأتي عند بدء التشغيل وعودة الاتصال والتركيز/نشاط الشاشات والفرع، وعند التحقق السابق للعملية المالية المتصلة؛ طلبات النشاط المتقاربة تُدمج ضمن نافذة 5 دقائق. يوجد طلب جارٍ واحد بدل طلبات سحب متراكبة.

الفحص الاحتياطي في الخمول بين ساعة وساعتين مع jitter. هذا ليس جدول إرسال كل جهاز كل دقيقتين، ولا ضمان ظهور فوري على شاشة خاملة. لا توجد شهادة زمن تسليم دائم خلال دقيقتين؛ الاتصال والحصص والتعارض والحالة المحلية كلها تؤثر. التصميم يخفف الطلبات الفارغة بدل polling كل 4 ثوان، دون تأجيل حفظ العملية محليًا.

## مسار المصادر

| الحالة | ما يحدث |
|---|---|
| حفظ محلي | إنشاء مصدر بمعرف فريد وشركة/فرع و group ، ثم حفظ الحالة والطابور ذريًا |
| push | تحقق الهوية والصلاحية والحقول والعلاقات وشروط رؤوس التعارض |
| قبول | حفظ المجموعة ورؤوسها في D1 ؛ إقرار محلي دائم قبل إزالة queue |
| pull | صفحات مصادر مرتبة؛ cursor يتقدم مع حالة الحفظ وليس قبلها |
| إعادة إرسال | المصدر نفسه يُعاد دون أثر مزدوج؛ changed-payload ليس تكرارًا مشروعًا |
| انقطاع/فشل | المصدر باقٍ في الطابور؛ الواجهة لا تدعي إقرار الخادم |

`sync_events_v2` سجل مصادر الأعمال، وليس نسخة من كلمات مرور أو جلسات. `sync_commit_groups` يحفظ اتساق المجموعة، و`sync_conflict_heads` يتيح رفض الكتابة القديمة. ليس ترتيب وصول الشبكة إذنًا باستبدال آخر تعديل.

## مبيعات مستقلة على أجهزة مختلفة

المبيعات المستقلة المدعومة تمر بإعادة مواءمة مدققة على`/api/sync/rebase` عند الحاجة، مع الحفاظ على معرفات الفواتير ومصادرها. يُعاد حساب الأثر المحلي ذريًا ثم يُنفّذ push الأصلي بتحقق الخادم؛ لا تُلغى شروط CAS عمومًا ولا يجري last-write-wins. هذا المسار لا يمنح تلقائيًا كل نوع تعديل أو مرتجع أو استعادة السياسة نفسها.

## تعارض قرار المالك

1. بعد 409 سببي غير قابل للمواءمة، تُرفع المجموعة الأصلية إلى صندوق الأدلة دون إقرارها كمالية مقبولة.
2. مالك الشركة الحقيقي، لا موظف admin مفوّض، يقرأ المقارنة ولقطة رؤوس حديثة من`GET /api/sync/conflicts`.
3. الاختيار الصريح ينفذ`PATCH` مع`execute:true` و`expectedHeads`. الطلب القديم دون execute يسجل نية فقط، ولا يُسمى تسوية.
4. إعادة تشغيل التاريخ والتحقق المالي يسبقان الإقرار. SQLguard داخل D1batch يمنع تغيّر الرؤوس أو تكرار قرار مختلف بين القراءة والالتزام.
5. اختيار المحلي ينشئ مصادر بديلة بمعرفات جديدة مع حفظ الأصل؛ اختيار الخادم يوثّق عدم قبول الأصل. receipt ثابت يحدد النتيجة. فهرس 0026 يربط معرفات الأصل بال receipt دون مسح JSON كل القرارات في كل push.
6. صاحب الطابور الأصلي يطلب`/api/sync/resolutions`. تُحسب النتائج من التاريخ الكامل أولًا، ثم تُصفى بالصلاحية/الفرع؛ المشتريات المحجوبة عن الكاشير لا تُنسى من حساب المخزون.
7. الجهاز يتحقق من تغطية طابوره كاملًا وصحة receipt والفرع والمؤشر، ثم يؤرشف aggregate السابق والمصادر ويثبت checkpoint والطابور والمعرفات في التزام محلي واحد. فشل التخزين يبقي الأصل كاملًا.

قرار المالك لا يحذف تعديلات معلقة تابعة لم تُراجع. ready:false أو تاريخ/نوع غير مدعوم يعني بقاء المصادر والانتظار/مراجعة أخرى، لا نجاحًا مصطنعًا. حد إعادة تشغيل التسوية 2000 حدث، وأدلة المجموعة 100 حدث/256KiB ، ومراجع العلاقات 50 ؛ اقرأ guards قبل توسيع الأحجام. لا تُحوّل create متعارض الهوية إلى update عشوائي.

## استرداد السجل القديم والعلاقات

السجل المحلي القديم قد يختلف عن الدائم أو يفتقد شركة/فرعًا. لا يُمسح عند الترقية. الأرشفة الموثقة أو الاسترداد يسبقان الانتقال للدائم. الشاشة الوقائية ليست سياسة تعطيل العمل عند كل ترقية؛ هي رفض الادعاء بأن حالة غير موثوقة صالحة ماليًا.

عند ورود فاتورة تتطلب صنفًا غير موجود، تُحفظ المجموعة في مراجعة العلاقات، ولا تمنع كل المصادر الجديدة بلا تفسير. الصنف القديم بلا branchId لا يُنسب إلا إذا أثبت التاريخ الكامل منشأه الفريد وفرعه المصرّح به، دون تعارضات أو نقل غير محسوم. تعديلات لاحقة مصرح بها في الفرع نفسه تُقبل في الإثبات؛ تاريخ أجنبي أو غير كامل يُرفض. الترطيب المحلي والدليل وإعادة المحاولة ذرية، ولا تعيد كتابة مصدر D1 القديم.

البيانات المالية/التقارير والإعدادات الحساسة تُحمى أثناء المراجعة غير المكتملة. نسخ المصدر يدويًا أو تغيير cursor لتجاوز الحماية قد يخفي فقدًا؛ ليست إجراءات تشغيل مقبولة.

## النسخ الاحتياطي

snapshot الحالي **version4** ويشمل هوية الشركة و syncCursor والإعدادات والفروع والمصفوفات المالية الكاملة. لا تعتمد وثيقة قديمة تشير version3 بوصفها تنسيق الاستعادة الحالي. `validateBackup` يرفض الشركة الأجنبية والنسخة الجزئية والمعرفات المكررة والعلاقات غير الصالحة والحقول الحساسة؛ النسخة لا تحتوي اعتماد الدخول.

النسخ المجدول ينتظر إقرار true ؛ false/throw ليس نجاحًا، وتُلغى إقرارات الجيل القديم. Backup حساب الشركة ليس بديلًا عن export إداري خاص لقاعدة D1 ؛ الأخير قد يحتوي اعتمادًا/بيانات حساسة ويجب أن يبقى خارج Git.

اختبارات التحقق وال rollback ناجحة، لكن لا يوجد اعتماد شامل لتمرين استعادة إنتاج كامل على جميع الأجهزة والتقارير. الاستعادة مصدر مالي/مزامنة له ترتيب وحدود، وليست تحميل JSON دون مراجعة. لا تخلط أرشيف الاسترداد بالدفتر الحالي أو تمحو archive حتى يُراجع.

## تشخيص قصير

ابدأ بالشركة/المستخدم/الفرع، ثم حالة التخزين وعدد queue والمؤشر وآخر طلب وحالة HTTP. اطلب requestID وأسماء المصادر بدون token أو password.401 جلسة، 403 صلاحية، 409 تعارض، 503 خدمة؛ quota أو IndexedDBblocked مشكلات محلية مختلفة. سجّل ما إذا كانت العملية محفوظة محليًا أو مقبولة على الخادم قبل أي إعادة محاولة يدوية.
